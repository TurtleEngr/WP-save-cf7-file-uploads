*** *The key fact:*
a single CF7 submission runs in one PHP request, and every step
happens in this order inside it:

1. =save-cf7-file-uploads= checks files in =wpcf7_before_send_mail=.
2. Flamingo saves the message in =wpcf7_submit=.
3. =contact-2-post= creates the post in =wpcf7_after_flamingo=.

Each request gets its own PHP memory. So when two people submit at the
same moment, their error lists can't mix unless they are written
somewhere shared, like a file. A shared file needs a per-submission
key. The form ID alone isn't enough, because two people can be filling
in the same form at once.

*** *Option 1: keep the errors in memory, with no file (simplest).*

=scf7fu_error_log()= appends to a =static= array and returns it, just
like =fC2pSaveAttachId()= does now in contact-2-post. Then
contact-2-post calls =scf7fu_error_log()= with no argument (guarded by
=function_exists=) and appends the list to the post. It is isolated
per submission automatically, needs no cleanup, and is about 10
lines. The downside is that the messages last only for that
request. You could also have it still call =error_log()= so the server
log keeps a copy.

*** *Option 2: save the errors in Flamingo's message meta.*
Hook Flamingo's =flamingo_add_inbound= filter (in
=class-inbound-message.php=) and add the errors to
=$args['meta']=. Contact-2-post already loads the message with =new
Flamingo_Inbound_Message($id)=, so it reads them from
=$tMsg->meta=. The errors stay tied to exactly that submission, show
up in the Flamingo admin, and last after the request. The cost is one
more hook. This filter runs for every Flamingo channel, so check that
a CF7 submission is active first.

*** *Option 3: write a file per submission.*
Put the file in =wp_upload_dir()['basedir'] . '/scf7fu-errors/'=,
named with a key made once per request, for example
=wp_generate_uuid4()= kept in a static. Contact-2-post then needs that
key, which has to come through a function or action anyway, much as in
Option 1. It reads the file and deletes it afterwards. This is the
most code, and it needs file locking and cleanup of files that are
never used, for example when =create_post= is off or the submission is
spam. It also needs an =index.php= or =.htaccess= file so the error
files can't be browsed. The only time it's worth it is if post
creation might later move to a separate request, such as cron.

*** *Option 4: one shared log file.*
Lines like =time | form_id | submission_key | message=, written with
=FILE_APPEND | LOCK_EX=. This is good for an audit trail, but
contact-2-post would have to read and filter it on every post. It also
still needs the per-submission key, so it doesn't fix the matching
problem by itself.

*** *My suggestion:*
Option 1 if the errors only need to appear in the post. Option 2 if
you also want to keep a record. A file adds keys, locking and cleanup
to solve a problem that one request already solves for free.
